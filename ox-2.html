공부 자료를 올리는 공용 칸이에요. 닉네임만 있으면 어느 기기에서든 올릴 수 있고, 목록은 닉네임·기기와 상관없이 모두에게 같은 최신 목록으로 보여요.

업로드한 자료는 앱에 자동으로 반영되지 않아요. 상태는 검토 중(pending_review)으로 시작하고, 채팅에서 Claude에게 자료를 확인해 달라고 하고 직접 반영하라고 말해 준 뒤에만 앱 자료에 반영돼요.

업로드가 파일 저장(Storage) 단계에서 new row violates row-level security policy (코드 AccessDenied)로 막히면, 원인은 앱이 아니라 uploads 버킷에 파일 올리기(INSERT) 정책이 없는 것이에요. uploads 테이블 기록은 정상으로 들어가고, 파일 본체를 담는 버킷 정책만 비어 있어요. 앱 코드로는 우회할 수 없어서, 프로젝트 소유자가 Supabase 대시보드의 SQL Editor에서 아래 SQL을 한 번만 실행하면 열려요. 이미 있는 정책은 같은 이름으로 교체되고, 데이터는 지워지지 않아요.

"Failed to fetch"처럼 요청 자체가 실패하는 경우는 서버 응답을 받기 전에 브라우저에서 막힌 거예요. 흔한 원인: CORS·프리플라이트 차단, 광고·추적 차단 확장 프로그램, VPN이나 회사·학교 네트워크의 방화벽, 사파리의 콘텐츠 차단. 맥 크롬이면 확장 프로그램을 끄거나 시크릿 창에서, 사파리면 콘텐츠 차단을 끄고 다시 시도해 보세요. 연결 테스트 버튼을 누르면 서버 상태 확인과 데이터 읽기를 단계별로 점검해 결과를 그대로 보여줘요. 연결이 안 돼도 입력한 내용은 이 기기에 계속 저장되고, 네트워크가 되면 자동으로 다시 동기화를 시도해요. 맥 크롬 주소창에서 Supabase 주소가 열리는데 앱에서만 실패한다면, 앱이 아니라 앱이 열린 환경 쪽 문제예요. 시크릿 창에서 열거나 확장 프로그램을 끄고 비교해 보세요.

            
사용 테이블: nicknames · user_progress · wrong_notes · blank_drafts · bulletin_posts(공용 게시판) · app_versions(공용 버전, id=1) · uploads(공용 자료 업로드 기록, 파일 본체는 Storage의 공개 uploads 버킷)

            
게시판과 앱 버전은 닉네임별로 나뉘지 않는 공용 데이터예요. 게시판 글의 작성자는 현재 닉네임이 자동으로 찍히고, 본인 글(작성자 닉네임이 현재 닉네임과 같은 글)만 수정·삭제 버튼이 보여요.

            
자료 업로드도 닉네임별로 나뉘지 않는 공용 데이터예요. 업로드한 자료는 앱에 자동 반영되지 않고, 상태가 pending_review(검토 중)로 남아 있다가 채팅에서 확인하고 직접 말해 준 뒤에만 반영돼요.
